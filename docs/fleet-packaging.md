# Fleet packaging — single shared install + wrapper identity (MS-25, U1)

Fork-side wiring only; never PR'd as code upstream (a docs note is the most
this earns there). Behavior-neutral: nothing here changes pi's CLI, defaults,
prompts, tool semantics, or output — it changes **where the bits come from and
what a seat can prove about them**.

## The contract

1. **One shared install.** `fleet-install.sh install` materializes an
   immutable `<root>/<version>-<manifest8>/` tree and flips `<root>/current`
   atomically. Every new seat resolves `current` at launch. A version change is
   one symlink flip; old installs are retired by hand (never auto-swept).
2. **Prebuilt bundle pinning.** `fleet-pin.json` pins version + package.json
   + `npm-shrinkwrap.json` + `dist/cli.js` + a manifest digest over `dist/`
   (sorted `relpath<TAB>sha512` lines), plus the wrapper's `node_flags` and
   `wrapper_rev`. Verification is fail-closed: a hash mismatch refuses install
   and refuses launch.
3. **Wrapper identity discipline.** `fleet-wrapper.sh` exports, per seat:

   | env | meaning |
   |---|---|
   | `PI_FLEET_PIN` | `<version>+<sha512(dist/cli.js)[0:8]>` — install identity (same derivation as the nix wrapper) |
   | `PI_FLEET_INSTALL` | resolved shared install path |
   | `PI_FLEET_WRAPPER_REV` | launcher/wrapper revision |
   | `PI_FLEET_NODE_FLAGS` | node flags actually in effect (identity-covered) |
   | `PI_CODING_AGENT_RUNTIME_ROOT` | compat: package root for the bridge |

   **Cohort contract for every memory probe:** group by
   `PI_FLEET_PIN` + `PI_FLEET_NODE_FLAGS` first; compare deltas only within one
   identity. A pin or flag change starts a new cohort — it is never folded
   into an existing one.

## Layout

```
packaging/fleet/
  fleet-pin.json       # the pin (generated by `compute`, checked in)
  fleet-install.sh     # compute | verify | install (fail-closed)
  fleet-wrapper.sh     # identity-disciplined launcher
docs/fleet-packaging.md  # this file
```

Root default: `${XDG_DATA_HOME:-~/.local/share}/pi-fleet`. Override per host
with `PI_FLEET_ROOT`. The launcher keeps the deployed argv semantics
(`exec -a pi node … dist/cli.js "$@"`; `argv[0]=pi` is ananicy-cpp's scheduler
identity) and takes nix-side wrapper args (e.g. `--import=<bridge>`) via
`PI_FLEET_NODE_ARGS`.

## Rollout path (MS-31 — separate change, not this deliverable)

1. `fleet-install.sh install --source <warm 0.99.0 bundle>` on the host.
2. `modules/home/pi.nix` exec line resolves `current/dist/cli.js` through
   `fleet-wrapper.sh` instead of the npx-cache lookup, passing its
   `--import=piCommandBridge` via `PI_FLEET_NODE_ARGS`.
3. Retire `~/.cache/pi-npx/<old>` by hand after the last pre-switch seat
   exits (never a sweep). The 0.84.x/0.85.1 caches (~467 MB) are then garbage.
4. Acceptance legs for MS-25: Nix build green (at this rollout) + the fleet
   memory table (MS-31's rollout table). No upstream table obligation while
   U1.

## Known ceilings

- Launch verification is the entry hash + version only; the full `dist/`
  manifest is checked at install time. A corrupted non-entry file is caught at
  the next `verify`/install, not at launch.
- The pin covers the package bundle, not the node binary. Node version rides
  the Nix pin (`nodejs_22`); a node bump is a `wrapper_rev` change.
- `compute` hashes are only as trustworthy as the source they were computed
  from — the pin records provenance (`pinned_from` in the register), not
  publisher attestation.
